# Step 0f decisions: web service and demo page

Background and the list of what 0f contains: `docs/decisions/0005-web-service-and-demo.md`. Decisions are taken one at a time, in this order: 1 framework and process layout, 2 API contract, 3 client identity, 4 caching, 5 feedback box, 6 article-number rule, 7 demo page, 8 memory and speed on the target server.

| # | Decision | Who, when |
|---|---|---|
| 1 | FastAPI with one worker process; bge-m3 is loaded inside it at start; at most 2 questions are embedded at the same time (semaphore). Not chosen: Flask/Gunicorn (no Pydantic link), a separate embedding service (two things to deploy, a network hop), Streamlit/Gradio (0005). Measured on the Mac CPU (8 cores, 12 French dev questions): bge-m3 takes about 1.0 GB loaded and peaks at 1.95 GB after queries; embedding one question takes a median of 156 ms (max 201 ms). The 2.5 GB of 0005 was a guess. The target server is not measured yet (decision 8) | User, 2026-11-11 |
| 2 | One JSON reply for `POST /ask` (`request_id`, `outcome`, `claims` with their citations, the 5 retrieved `articles`, `reason`, disclaimer) in the same shape for every outcome. Status 200 for answers and for refusals about the question (weak search, model refusal); 429 with `Retry-After` for a client limit; 503 for the cost cap and the switch. The retrieved articles come back in every case. Question limited to 500 characters (422 above): the 128 French gold questions have median 88, 95th percentile 147, maximum 220. `lang` defaults to `fr`; the demo does not expose English. `POST /search` returns only the articles with similarities and is never limited. Not chosen: streaming (the answer must pass the citation check before it is shown), a job id with polling (not needed for a 2 s reply) | User, 2026-11-11 |
| 3 | A client is the visitor's IP address, read from the header that the proxy in front of the service sets (`X-Forwarded-For` by default, the name is a setting `CLIENT_IP_HEADER` because the deployment is not chosen), and stored only as the daily keyed hash of `trace.client_hash`. The header is trusted only when the request comes from our own proxy (uvicorn `--forwarded-allow-ips`), otherwise a visitor could invent an address per request; the proxy replaces any header the visitor sends. No address: all such requests share one count (`limits.py`). Search is never limited. Known limit: people behind one shared address share a quota; the global cap of $0.10 a day is the backstop. Not chosen: a cookie id (cleared at will, consent question), IP plus cookie (more states), an invite token per person (friction; open or behind a link is decision 7). Not tested on a shared network | User, 2026-11-11 |
| 4 | Exact-match answer cache in a Postgres table. Key: hash of the normalised question (lowercase, spaces collapsed) with the model, prompt id, threshold and data version, so a change of any of them gives a new key. Value: the finished reply. Only `answered` and `refused_by_model` are cached (never errors, limits or the switch-off). A hit skips the embedding and the model, is not counted in the visitor's quota (the per-minute limit still applies), and the reply says `cached: true`. A thumbs-down removes the entry (decision 5). Entries expire after 7 days (a guess, untested; the version in the key already prevents stale answers). Only the hash of the question is stored, not its text. `legalrag cache-warm` runs the checked example questions after a deploy. Measured: one answer costs about $0.0004 and 1.6 s of model time; real repeat rates are unknown until there is traffic. Not chosen: no cache, a cache in process memory (emptied at each deploy), a semantic cache (similar legal questions can have different answers) | User, 2026-11-11 |
| 5 | Feedback box, option B. Under each answer: 👍 / 👎; after a 👎 an optional form with a kind (wrong answer, wrong citation, missing article, other) and an optional comment; a 👍 can carry a comment too. `POST /feedback {request_id, value, kind?, comment?}`; comment at most 500 characters; a new column for the kind; a notice "do not write personal data, kept 30 days". Comments live in `query_traces` (30-day expiry), are shown to no visitor, and are read by the owner with `legalrag traces`; `traces export` turns failures into candidate evaluation questions. The `request_id` must exist, one vote per request (a new one replaces it), 10 a minute per client. A 👎 removes the cached answer only when the voter is the client who got it (otherwise a stranger could clear answers and make the service pay for new ones). The user also asked for a contact line at the bottom of the page: a link to the GitHub issues of the repository (issues are enabled) and an email address. Which address to show, and whether to write it in a form that scrapers read less easily, is for the user to say when the page is built (decision 7); no address is published before | User, 2026-11-11 |
| 6 | The article-number rule (`articlenum`) is on for the service: a question that names an article gets that article first, by a direct lookup, before the search results. Evidence so far is thin: on dev it changes 1 of 65 rankings (`smoke-08`, outside the top 5 to rank 1), and it acts only when a number is named. Before it is built into the service it is tested on a small sample (about 15 variants of "Que dit l'article X ?" with real article numbers and about 15 questions that name no article), and the numbers go to the user. The gate gets a test for it on articles that are in the fixture. Not chosen: off (a visitor who types an article number gets a refusal), on for `/search` only | User, 2026-11-11 |
| 8 | Memory and speed on the target server are measured at the start of the deployment stage, when the server is known; the Mac figures of decision 1 are the reference until then. Moved out of 0f | User (implied by going on to decision 7), 2026-11-11 |
| 7 | The demo page. **7a** French page with an English toggle for the page text (questions and answers stay French). **7b** the measurements are a sub page `/method` (summary table of about six numbers, the method in a few sentences, the known limits, links to the full tables on GitHub; no copy of the full tables), plus one headline line with a link on the main page; the user proposed the sub page, 2026-11-11, and the summary content is the assistant's proposal. **7c** open to everyone: no key; the per-client limits, the cost cap of $0.10 a day and the kill switch bound the cost; known risk: the cap can run out before a recruiter arrives, who then still gets the articles and the cached examples. Not chosen: a key in the link for typing new questions, two caps. The user relies on the answer filter and the log: the citation check, the weak-search refusal and the model refusal filter unsupported content, and every request is traced for 30 days with its question; there is no filter on what a visitor types, and prompt injection is untested, so the build includes a small test (about 10 injection-style questions) and the numbers go to the user. A cache hit needs its own outcome (`cache_hit`) in the table check (migration). **7d** the example questions (about 6 from the dev set: good answers, one refusal where the law is silent, one false premise corrected) and **7e** the contact line (GitHub issues link; which email to show) are settled at the build, checked by the user | User, 2026-11-12 |

## Build notes (part 1, the service, 2026-11-13)
- New folder `web/` (`app`, `schemas`, `build`), after `evaluation` and before `cli` in the dependency order; `legalrag serve` starts it (one worker, `proxy_headers` off).
- Decision 3 as built: the client header is read by the app itself (`Settings.client_ip_header`, env `CLIENT_IP_HEADER`) and not by uvicorn's `--forwarded-allow-ips`. It is only safe when the service is reachable through our proxy alone (bind to localhost or the container network), because a visitor could write the header. Without a named header the connection address is used.
- Decision 2 detail not discussed before: a model failure (`llm_error`, `parse_error`) answers 502 with the articles; the other refusals stay 200.
- Search mode is traced like answers (`mode = search`; outcome `answered`, or `refused_weak_retrieval` when nothing is close enough) and never limited. A failed trace write is logged and the visitor still gets the reply.
- Measured on the real service on the Mac (CPU, the full database with its 8 chunking runs): `/search` 0.6 to 0.8 s when warm (embedding about 0.16 s of it), but 7 to 10 s for the first requests after the server had been idle. The exact scan sorted the vectors of all 8 runs; after the 7 comparison runs were deleted (EXPERIMENT.md, 2026-11-13) the same query takes 0.10 s warm instead of 0.34 s. The slow first request after a pause (a cold cache is a guess) is still to look at in the deployment stage (decision 8).
- Not done yet in the service: the cache and its `cache_hit` outcome (part 2), the article-number rule (part 3), the pages (part 4).
